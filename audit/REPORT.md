# Sangham product audit — 3–4 November 2026

## 1. Executive Summary

**Verdict: suitable for private experimentation with disposable data; not ready to be trusted as a real cash ledger.**  
The intended audience is Kerala residents aged 30–65; the owner confirmed testing stage and no online payments.  
The stack is Flutter/Dart (Android and web configurations), Express/Node, MongoDB/Mongoose and custom JWT authentication; the client points at Render.  
The main risk is financial correctness: borrowers can certify their own repayments, simultaneous writes lose balance changes, and errors can leave half-written receipts.  
A member loan-detail API/type mismatch crashes the screen; the Android release APK lacks internet permission and is debug-signed.  
The existing 59 backend checks and one Flutter test pass, but several checks encode the wrong financial behavior.  
UI/accessibility/performance scores below are provisional: browser inspection covered login/signup; authenticated screens were assessed from source and targeted mocked-widget/API probes, not real-device user testing.

**What was actually checked**

- Reviewed API routes, authorization, Mongo schemas, loan arithmetic/scheduler, client API/session/navigation flows, screens, Android/web configuration, tests and relevant Git history.
- Existing local backend suite: **59/59 passed**, using a disposable MongoDB.
- Existing Flutter analyzer: **no issues**; existing Flutter test: **1/1 passed**.
- Added independent local API probes: **14 observations** reproduced authorization, validation and accounting defects. All mutation tests used a fresh loopback MongoDB; no live database was changed.
- Added mocked-network Flutter audit probes: **4/4 completed**. These deliberately characterize current behavior; “pass” does not mean the app is safe. Confirmed the loan-detail type crash, malformed money confirmation, persistent admin shell after 401 and ListTile feedback assertion. The one 320×480, 200%-text login test emitted no overflow; that does not certify all screens.
- Web release build succeeded. main.dart.js: **3,031,733 bytes**, **893,194 gzip bytes** measured locally; hosting compression and Core Web Vitals were not measured.
- Android release build succeeded: **54,434,520 bytes (51.9 MiB)** universal APK. aapt confirmed no INTERNET permission; apksigner confirmed **CN=Android Debug**.
- Browser inspected login/signup, including 360×640 portrait, 1280×720 desktop and 640×320 landscape. Inspected the enabled accessibility tree.
- npm audit: **8 affected packages including dev**, **7 production**. Production ratings: 1 critical, 2 high, 4 moderate. Those are package-advisory ratings, not eight independently exploited app vulnerabilities.
- Existing user edits in server/routes/dashboard.js, members.js and transactions.js were preserved. Build-generated local.properties changes were restored. Only audit artifacts were added; proposed fixes were not applied.

Security reference baseline: [OWASP Top 10:2025](https://top10.owasp.org/2025/), [ASVS 5.0.0](https://asvs.owasp.org/) and [MASVS](https://mas.owasp.org/MASVS/). Accessibility reference: [WCAG 2.2](https://www.w3.org/TR/WCAG22/).

## 2. Critical Blockers

1. **A01 — Borrower-controlled official debt:** a member token successfully changed a ₹10,000 loan to repaid without administrator confirmation of received cash. A ledger must not treat “I paid” as proof that cash was received.
2. **A02 — Money records are not atomic or concurrency-safe:** eight successful ₹100 repayments left ₹9,700 instead of ₹9,200; a failed transaction save still reduced the debt. This can happen through normal retries and two admins, not only malicious use.
3. **A03/A04/A05 — Interest, duplicate posting and independent receipt editing can corrupt the books:** the same cash can be recorded twice, already-paid interest can reappear, and deleting a disbursement does not remove or reverse its loan.
4. **A06/A07/A08/A09 — Access is not safe for real personal/financial data:** historical credentials need rotation verification; phone-derived passwords, unapproved public admission, roster disclosure and nonrevocable long sessions must be addressed.
5. **A12/A14 — The intended product cannot reliably complete core release journeys:** the release APK cannot access the network; loan details fail to build because the API and UI disagree on the rate type.
6. **A10/A11/A13 — Patch the vulnerable parser, isolate destructive scripts and fix the cash confirmation before broader testing.**

The two Critical findings are A01/A02. The additional High findings are launch blockers too; “testing stage” reduces current exposure, not the seriousness of the design defects.

## 4. What's Done Well

- Administrative writes generally have server-side adminOnly checks; user-specific loan/attendance/transaction reads generally compare the authenticated user ID. Existing cross-user denial checks passed.
- Registration fixes role to user instead of trusting the submitted role. The test verifies this. Preserve the control even if registration becomes invite-only.
- Middleware reloads the user and enforces isActive, so disabling a member blocks an already-issued token; the local E2E test verified this.
- Passwords are bcrypt-hashed with cost 10 and excluded from member lists. The failure is weak credentials/session policy, not plaintext password storage.
- Attendance has a unique user/day index; transactions and loans have useful basic indexes. Attendance month navigation rejects stale responses.
- ApiService centralizes HTTP status checks, timeout handling and JSON/network errors; many screens have retry/empty states, mounted guards and submission guards.
- The Material 3 theme, strong primary green, labelled text fields, explicit attendance marking and confirmation dialogs provide a useful base.
- Existing disposable-MongoDB E2E infrastructure and working Android/web release builds are worth keeping. Replace incorrect business expectations rather than discarding the test infrastructure.
